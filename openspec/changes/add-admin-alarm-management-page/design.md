## Context

当前报警模块已经具备操作员视角的最小闭环：后端能够按用户授权区域返回报警汇总、列表、详情和单条确认结果，Socket.IO 连接也会在建连时把用户加入对应的报警区域房间，并推送首屏快照与增量更新。这套实现已经满足“本区域查看 + 单条处理”的目标，但它把访问范围和交互粒度都固定在操作员语义上。

新 change 面向的是 admin 工作台，而不是操作员抽屉的继续堆叠。因此设计需要同时解决两个结构性问题。第一，`admin` 必须天然拥有全系统启用区域的视角，而且这个视角必须在 HTTP 查询、`GET /api/users/me/alarm-areas` 和 Socket 房间初始化三个入口保持一致，不能靠前端拼装“全选区域”来模拟。第二，批量确认不能退化成“前端循环调单条接口”，否则统一备注、部分成功反馈、并发冲突和广播行为都会分散在页面逻辑里，难以保持稳定。

此外，管理页还需要一套正式的 admin 管理接口来支撑普通用户目录和区域授权维护。当前开发环境中的 `mockUsers` 已经承担登录身份来源，但报警区域管理尚未形成对 admin 页友好的用户目录和目标用户上下文读取契约。

## Goals / Non-Goals

**Goals:**

- 为 admin 建立统一的全区域报警访问模型，并让该模型同时驱动 REST、Socket 和“我的报警区域上下文”返回值。
- 定义一个明确的批量确认接口，支持“当前页可见未确认项”语义、统一备注写入以及部分成功结果回传。
- 为 admin 报警管理页补齐正式的普通用户目录和目标用户报警区域上下文读取/写入接口。
- 将管理页定义为独立路由页面，默认打开历史模式，同时与现有 HMI 风格保持一致。

**Non-Goals:**

- 不改造现有报警事件持久化模型，不新增专门的 admin 报警表或批量确认中间表。
- 不把普通用户提升为支持批量确认的角色；本 change 中批量确认入口只面向 admin 页面。
- 不引入完整 RBAC 体系或新的角色层级；角色仍维持 `admin` 与 `user` 两档。
- 不替换现有操作员报警中心抽屉；它继续承担实时查看和单条确认职责。

## Decisions

### 1. admin 全区域视角采用统一访问范围解析层，而不是写死在各接口里

现有实现把区域解析拆散在多个函数里：REST 查询通过 `getAuthorizedAlarmAreaIds(userId)` 获取区域集合，Socket 连接初始化时也独立调用同一个函数，而 `GET /api/users/me/alarm-areas` 则直接读取 `user_area` 关系。这会导致 `admin` 全区域语义无法通过一个点统一注入。

本 change 将访问范围求值提升为统一的“报警访问范围解析层”。建议新增一个面向已认证用户的统一结果对象：

```ts
interface AlarmAccessScope {
  mode: 'all-enabled' | 'assigned';
  area_ids: number[];
  default_area_id: number;
  areas: Array<{
    area_id: number;
    area_code: string;
    area_name: string;
    is_default: boolean;
  }>;
}
```

其解析规则固定为：

- `user.role === 'admin'` 时，`mode = 'all-enabled'`，`areas` 取 `alarm_area` 表中全部启用区域，按 `sort_order` 排序。
- `user.role === 'user'` 时，`mode = 'assigned'`，`areas` 继续来自 `user_area` 与 `alarm_area` 的关联结果。
- `default_area_id` 对 `admin` 采用合成值，不要求在 `user_area` 中持久化；默认取排序后的第一个启用区域，用于兼容现有“单默认区域”前端契约。

这样处理的原因是，`admin` 的“全量”是角色语义，不是授权数据录入结果。只要继续要求为 `admin` 维护一组覆盖全区域的 `user_area` 记录，就会把角色语义和配置数据耦合在一起，形成重复来源和潜在漂移。

统一解析层应成为以下入口的唯一上游：

- `GET /api/users/me/alarm-areas`
- `GET /api/alarm-areas`
- `GET /api/alarms/summary`
- `GET /api/alarms`
- `GET /api/alarms/:id`
- Socket.IO 连接建立时的房间加入与首屏快照初始化

访问范围模型如下：

```text
                ┌──────────────────────────┐
                │ resolveAlarmAccessScope  │
                └─────────────┬────────────┘
                              │
                ┌─────────────┴─────────────┐
                │                           │
          role = admin                role = user
                │                           │
      all enabled alarm_area         user_area ∩ enabled area
                │                           │
                └─────────────┬─────────────┘
                              │
         REST summary/list/detail, me context, Socket rooms
```

### 2. admin 的“我的报警区域上下文”返回合成全区域结果，以兼容现有前端契约

虽然 admin 的主要入口会转向独立管理页，但现有系统里页头报警角标、右侧报警中心抽屉和 Socket 首屏快照都仍依赖“当前用户的报警区域上下文”。为了避免新增一套 admin 专用上下文接口，本 change 保持 `GET /api/users/me/alarm-areas` 的响应结构不变，只调整其 admin 语义。

也就是说：

- `admin` 请求该接口时，返回所有启用区域。
- `default_area_id` 返回排序后的第一个启用区域。
- `areas[].is_default` 只有默认区域为 `true`，其余为 `false`。

这样可以让现有报警中心在 admin 登录时继续可用，同时不会要求前端为 admin 单独分叉“我的区域”接口解析逻辑。

### 3. admin 用户目录走正式管理接口，且只暴露普通用户

报警管理页需要在“区域授权配置”模式中浏览可配置用户列表。当前项目存在通用 mock `/api/users`，但它既没有 admin 权限门控，也不是为报警管理场景设计的稳定契约。本 change 为此补一组管理接口，并把“只列普通用户”写成服务端规则，而不是交给前端过滤。

建议新增：

- `GET /api/admin/alarm-users`
- `GET /api/users/:userId/alarm-areas`
- 继续保留现有 `PUT /api/users/:userId/alarm-areas`

其中：

- `GET /api/admin/alarm-users` 只返回 `role = 'user'` 的目录项。
- `GET /api/users/:userId/alarm-areas` 和 `PUT /api/users/:userId/alarm-areas` 都要求调用方是 admin，且目标用户必须是普通用户。
- 开发环境下，这个用户目录继续复用当前登录系统同源的 mock 用户仓库；未来替换真实用户来源时，接口语义保持不变。

为避免把无效 `userId` 写进 `user_area` 形成孤儿授权记录，目标用户校验以当前认证系统同源的用户来源为准。也就是说，管理接口在写入或读取目标用户区域上下文之前，必须先确认该 `userId` 对应用户真实存在且 `role = 'user'`；不存在、角色不符或目标为 `admin` 都按同一类非法管理对象处理并直接拒绝。

推荐目录返回结构为：

```json
[
  {
    "id": 2,
    "username": "user1",
    "email": "user1@example.com",
    "role": "user"
  }
]
```

目标用户区域上下文读取结构与 `GET /api/users/me/alarm-areas` 保持一致：

```json
{
  "user_id": 2,
  "default_area_id": 1,
  "areas": [
    {
      "area_id": 1,
      "area_code": "AREA-A",
      "area_name": "A区",
      "is_default": true
    }
  ]
}
```

### 4. 批量确认接口采用“显式提交当前页项”而不是“重放查询条件”

“确认当前页可见未确认项”是一个强前端语义：当前页由前端已经拿到的筛选条件、分页参数和返回结果共同定义。若后端接口只接收查询条件再自行重算“当前页”，就会引入两个问题：

- 前端眼中的当前页与后端重算结果可能在请求瞬间已经发生漂移。
- 后端必须重复承担排序、分页和“只取可见项”的二次解释，接口语义会变得含糊。

因此，批量确认接口固定为“前端显式提交当前页可见未确认项的最小确认集”，每项至少包含 `alarm_id` 和 `expected_version`。统一备注在请求体顶层给出一次，由后端在每条成功确认的日志中复制写入。

建议接口为：

- `POST /api/admin/alarms/batch-ack`

请求体建议如下：

```json
{
  "operator_note": "交接班统一确认",
  "items": [
    {
      "alarm_id": 101,
      "expected_version": 3
    },
    {
      "alarm_id": 108,
      "expected_version": 1
    }
  ]
}
```

此接口要求：

- 调用方必须是 admin。
- `items` 最大长度不超过当前报警列表 `page_size` 上限，默认以 `200` 为硬上限。
- 后端逐条验证该报警当前是否仍在调用方可见区域范围内。
- `operator_note` 为可选字符串；如果提供，则在每条成功确认的 `alarm_event_log` 中以 `payload_json.operatorNote` 保存。

### 5. 批量确认采用部分成功语义，逐条独立提交，而不是整批事务回滚

当前单条确认的并发模型基于 `expected_version`。这意味着批量确认天然会遇到“部分条目已被其他人抢先确认或发生版本变化”的情况。如果把整批确认放进一个大事务，并在任意一条冲突时整体回滚，就会让管理页体验过于脆弱，也不符合“当前页批量处理”的目标。

因此，本 change 约定批量确认为部分成功模型：

- 每条报警独立执行与单条确认等价的状态校验与日志写入。
- 某条冲突、已确认或不可见，不影响其他条目的成功提交。
- 结果中逐条返回处理状态，前端据此提示并整体刷新当前列表页与详情。

建议响应结构为：

```json
{
  "requested_count": 2,
  "acked_count": 1,
  "results": [
    {
      "alarm_id": 101,
      "status": "acked"
    },
    {
      "alarm_id": 108,
      "status": "conflict"
    }
  ]
}
```

其中 `status` 固定取值建议为：

- `acked`: 本次成功确认并写入日志
- `already_acked`: 请求到达前已被确认，不再重复写日志
- `conflict`: 版本冲突
- `not_found`: 当前用户不可见或记录不存在

这里刻意不返回“整批失败”语义，也不为 `conflict` 或 `already_acked` 条目额外返回最新版本号。管理页提交批量确认后，前端统一按“整页重拉当前列表、汇总和详情”的策略恢复一致状态，避免为了减少一次请求而把返回结构和页面状态机变复杂。

批量确认数据流如下：

```text
当前页列表结果
      │
      ├─ 前端筛出可见未确认项
      │
      └─ POST /api/admin/alarms/batch-ack
                 │
                 ├─ 逐条校验可见范围与 expected_version
                 ├─ 成功项写 alarm_event + alarm_event_log
                 ├─ 统一备注复制写入每条成功日志
                 └─ 返回逐条结果 + 汇总计数
```

### 6. 批量确认复用现有单条确认核心逻辑，并按成功项逐条广播

虽然接口是新的，但数据库语义不能产生第二套确认实现。本 change 约定批量确认内部复用单条确认的核心状态迁移逻辑：

- 仅当 `ack_state = unacked` 且版本匹配时，把主记录更新为 `acked`
- 写入一条 `action = ack` 的 `alarm_event_log`
- 记录 `acked_by_user_id`、`acked_by_name`、`acked_at`

实现层可以将当前 `ackAlarmEvent()` 内的“单条确认事务”抽成可复用私有过程，再由批量确认服务循环调用。这样既能避免复制业务逻辑，也能保持单条与批量的审计结果完全一致。

对 Socket 广播，本 change 沿用现有单条确认后的增量推送语义：

- 每条成功确认的报警都生成一条 `alarm:upsert`
- 后端按受影响区域去重后重新计算并推送 `alarm:summary`

由于批量确认可能覆盖多个区域，最务实的做法是：`alarm:upsert` 仍按成功项逐条发送，但 `alarm:summary` 不再对每条成功项重复重算，而是对本次请求中受影响的区域集合去重后最多刷新一次。这样既保持现有操作员侧事件语义不变，也避免批量确认时出现不必要的汇总重算风暴。

### 7. admin 报警管理页采用独立路由 + 双模式工作台，默认打开历史模式

管理页不继续复用右侧报警抽屉，而是在 `HomePage` 下新增独立子路由，例如：

- 路由路径：`/alarm-management`
- 路由名称：`alarm-management`

页面内部采用一个工作台、两个主模式：

- `历史管理`：默认模式，进入页面时即打开
- `用户区域配置`：用于管理普通用户的报警区域授权

推荐页面骨架如下：

```text
┌──────────────────────────────────────────────────────────────┐
│ 报警管理                                                    │
├──────────────────────────────────────────────────────────────┤
│ 模式切换: [历史管理] [用户区域配置]                         │
├──────────────────────────────────────────────────────────────┤
│ 历史管理模式                                                │
│  查询条件栏  批量确认按钮  分页信息                         │
│  ┌──────────────────────┬─────────────────────────────────┐ │
│  │ 报警列表             │ 报警详情 / 操作日志             │ │
│  └──────────────────────┴─────────────────────────────────┘ │
├──────────────────────────────────────────────────────────────┤
│ 用户区域配置模式                                            │
│  ┌──────────────────────┬─────────────────────────────────┐ │
│  │ 普通用户目录         │ 区域勾选 / 默认区域 / 保存      │ │
│  └──────────────────────┴─────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────┘
```

这样设计的原因是，历史检索与用户授权配置都属于高密度管理操作，但不适合同时挤进一个三栏常驻布局。双模式工作台能在保持单一路由入口的前提下，把默认焦点放在“历史管理”，同时保留授权配置能力。

在访问控制上，管理页不只依赖侧边栏隐藏入口，而是同时具备两层防线：

- 侧边导航仅对 `admin` 显示管理页入口。
- 前端路由本身也按当前登录用户角色做 admin 守卫，防止普通用户通过手动输入 URL 直接进入管理页壳层。

### 8. 前端的当前页批量确认行为固定为“可见且未确认项”，并在提交后整页刷新

管理页中，批量确认按钮不会让用户手动勾选任意跨页条目，而是固定作用于“当前页结果中 `ack_state = unacked` 的可见项”。这与用户已经拍板的业务语义完全一致，也能显著降低交互复杂度。

前端处理流程固定为：

1. 读取当前列表页返回的 items
2. 过滤出 `ack_state = unacked` 的可见项
3. 生成 `alarm_id + expected_version` 列表
4. 提交统一备注
5. 根据响应提示“成功 / 已确认 / 冲突 / 不可见”计数
6. 重新拉取当前页列表、汇总和当前选中详情

这里要求“提交后整页刷新”而不是在前端本地逐条乐观更新，原因是：

- 历史页默认是管理页主模式，批量确认后涉及的状态和排序可能整体变化。
- 当前系统已有单条确认冲突后的重拉约定，批量确认延续这一策略更一致。
- Socket 广播会同时更新其他打开的报警界面，本页直接重拉能避免本地拼补状态过多。

进一步地，admin 管理页本身不接入报警 Socket 增量事件，也不直接复用现有操作员报警中心的 `alarmCenter` store。管理页保持拉取式刷新模型：进入页面时加载，切换分页或筛选条件时重新请求，批量确认或区域授权保存后整页重拉。这样可以把“当前页可见集合”的定义稳定地留在前端查询结果上，而不是交给实时事件持续扰动。

## API Boundary Summary

本 change 新增或修改的主要接口边界建议如下：

- `GET /api/admin/alarm-users`
  - admin-only
  - 只返回普通用户目录

- `GET /api/users/:userId/alarm-areas`
  - admin-only
  - 读取指定普通用户的报警区域上下文

- `PUT /api/users/:userId/alarm-areas`
  - admin-only
  - 继续承担整组替换用户报警区域授权关系

- `POST /api/admin/alarms/batch-ack`
  - admin-only
  - 批量确认当前页可见未确认项，支持统一备注

- `GET /api/users/me/alarm-areas`
  - admin 时返回合成全区域上下文
  - user 时保持现有授权区域上下文语义

## Risks And Mitigations

### 风险 1：admin 全区域语义只在 HTTP 生效，Socket 仍停留在旧授权模型

如果只修改 REST 查询，不修改 Socket 初始化时的区域解析，admin 在独立管理页里看到的全局历史结果和页头/抽屉里的实时汇总就会产生割裂。

缓解方式是把区域求值统一收口到访问范围解析层，并明确 Socket 建连也必须复用该结果。

### 风险 2：批量确认若采用大事务，会让单条冲突放大成整批失败

这会让“当前页批量处理”的可用性变差，尤其在多管理端并发操作时更明显。

缓解方式是采用逐条独立提交和部分成功响应模型。

### 风险 3：用户目录如果复用现有通用 mock `/api/users`，会把管理页耦合到开发接口

这样既不稳定，也无法表达“只列普通用户”的强规则。

缓解方式是定义专用 admin 用户目录接口，哪怕底层当前仍然读取同一份 mock 用户源。

### 风险 4：admin 默认历史模式下，批量确认按钮可能面对“当前页无未确认项”的空动作

这是正常场景，不应视为错误。

缓解方式是前端在当前页无未确认项时禁用按钮，并提示“当前页无可确认报警”。
