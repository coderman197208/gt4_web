## Why

现有 `add-area-aware-alarm-module` 已经为操作员建立了按区域过滤的报警中心、历史查询和单条确认闭环，但它的交互重心仍然是“当前登录用户处理自己可见范围内的报警”。对于管理人员而言，系统还缺少一套独立于操作员抽屉面板之外的工作台，无法在统一界面中完成全系统历史检索、普通用户报警区域授权配置，以及面向当前查询结果页的批量确认操作。

这一缺口在当前实现里表现得比较具体。第一，`admin` 身份并不会自动获得全系统报警区域可见范围，现有 REST 查询和 Socket 初始化仍然依赖用户区域授权关系，不能自然形成管理视角的全局监控。第二，报警区域配置虽然已有写接口，但缺少面向管理页的完整用户目录与目标用户上下文读取能力，管理人员无法稳定浏览和维护普通用户的区域授权。第三，现有报警确认只有单条语义，无法满足“对当前页可见未确认项做批量确认，并为每条确认日志写入统一备注”的新需求。

因此，需要新增一个独立的 admin 报警管理页，并将其作为现有报警模块之后的下一阶段 change 单独推进，而不是继续挤入现有操作员报警中心的交互边界里。

## What Changes

- 新增一个仅面向 `admin` 的独立报警管理页，作为 `HomePage` 子路由接入现有应用壳层，默认打开“历史”视图，并保持与 `MainMonitorView` 同源的工业 HMI 风格。
- 扩展报警区域访问控制语义，使 `admin` 在报警 REST 查询、首屏快照和实时汇总场景中默认拥有全系统所有启用区域的可见范围，而普通用户仍按 `user_area` 授权范围过滤。
- 为管理页补齐普通用户目录与用户报警区域上下文读取/写入能力，管理页中的用户目录只列出普通用户，不包含其他 `admin` 账号。
- 新增“确认当前页可见未确认项”的批量确认能力，允许管理人员填写一条统一备注，并将该备注写入每条成功确认的报警日志。
- 保持现有操作员报警中心抽屉继续承担实时查看和单条处理职责，不把管理型历史检索、区域配置和批量操作强行并入现有抽屉交互。

## Capabilities

### New Capabilities

- `admin-alarm-management-page`: 系统必须提供一个 admin 专用的独立报警管理页，支持以历史视图为默认入口，在同一工作台中完成报警检索、详情查看、分页操作和授权管理。
- `alarm-current-page-batch-ack`: 系统必须支持对当前页可见的未确认报警执行批量确认，并允许提交一条统一备注，将其写入每条确认成功的报警日志。
- `admin-user-alarm-area-management`: 系统必须支持管理人员浏览普通用户目录、读取指定普通用户的报警区域上下文，并整组替换该用户的授权区域和默认区域。

### Modified Capabilities

- `alarm-area-access-control`: 扩展现有区域访问控制语义，使 `admin` 默认可访问全系统所有启用报警区域，并可在管理场景下读取普通用户的报警区域上下文；普通用户仍然只能访问自身授权区域。

## Impact

- 受影响的前端范围包括新的 admin 报警管理页、路由注册、侧边导航显示逻辑，以及与现有报警 API/状态管理并行或复用的管理页数据装配层。
- 受影响的后端范围包括报警区域授权解析逻辑、admin 用户目录与目标用户区域上下文接口、批量确认接口，以及与这些能力配套的权限校验。
- 受影响的共享契约范围包括批量确认请求/响应模型、管理页用户目录项、目标用户报警区域上下文读取结果，以及可能需要补充的分页/筛选查询参数类型。
- 验证重点包括：admin 在 HTTP 与 Socket 侧都能获得全系统区域视角；普通用户权限不被放宽；管理页默认进入历史视图；批量确认仅作用于当前页可见未确认项；统一备注会落入每条确认日志。
