# 重构报警功能

## 目标与领域语义

- 报警采用不可变事件模型：每次发布均新增一条 `Alarm Event`，重复内容不合并、不去重。
- 确认仅表示操作员已阅，不表示故障恢复或清除。
- 本期不维护活动报警、恢复状态或清除事件；原有 `Clear` 路径应删除。
- 报警区域可选。空区域表示全厂报警，界面显示为“全厂”。本期所有用户查看全部区域，不做用户区域过滤。
- PostgreSQL 是报警事实源；Redis 仅发送数据已变化的瞬时通知，不保存报警记录。

## 数据库

使用显式部署脚本 `gt4_web/doc/database/alarm_event.sql` 创建表，应用不得在启动时自动建表。

```sql
CREATE TABLE public.alarm_event (
	id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
	message text NOT NULL,
	area varchar(100) NOT NULL DEFAULT '',
	occurred_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP,
	acknowledged_at timestamptz NULL
);

CREATE INDEX alarm_event_occurred_at_id_idx
	ON public.alarm_event (occurred_at DESC, id DESC);
```

- 确认状态由 `acknowledged_at IS NOT NULL` 推导，不增加布尔字段。
- 数据库负责生成事件 ID 和发生时间，避免应用主机时钟差异。
- 本期不自动清理历史数据；后续根据增长量单独制定归档策略。
- `gt4_app` 和 `gt4_web` 启动时均验证 `alarm_event` 表存在，缺表时终止启动并明确报错。

## C++ 报警发布

### 范围

项目目录：`gt4_app/AlarmPublisher`。

删除原有 `AlarmRaiseRequest`、`AlarmClearRequest`、`AlarmPublishResult`、`Raise`、`Clear`、Redis 事件缓存和不再使用的 JSON 逻辑。称重恢复正常或关闭称重功能时不再发布清除事件。

### 公开接口

仅保留以下公开接口：

```cpp
class AlarmPublisher
{
public:
	AlarmPublisher(pqxx::connection& database, sw::redis::Redis& redis);

	bool publish(const std::string& message, const std::string& area = "");
};
```

- 发布器使用注入的 PostgreSQL 和 Redis 连接，不读取配置、不自行创建或重连连接。
- TubeTrack 先初始化 PostgreSQL 和 Redis，再构造 `AlarmPublisher`。
- `message` 去除首尾空白后不得为空；消息正文使用 `text`，不得截断。
- `area` 去除首尾空白，最长 100 个字符；校验失败返回 `false` 并记录日志。
- 发布流程先插入 `alarm_event` 并提交，再向 Redis 频道 `AlarmChanged` 发布新事件 ID。
- 数据库写入失败时返回 `false` 并记录错误，但调用方继续生产流程；本期不增加本地队列或自动重试。
- 数据库提交成功后即返回成功语义。Redis 通知失败只记录错误，`publish()` 仍返回 `true`，避免调用方重试生成重复事件。
- 当前 TubeTrack 报警发布与其他数据库访问位于同一工作线程，继续复用其 PostgreSQL 连接。

## Web 后端

### 共享数据契约

在 `packages/shared/src/alarm_types.ts` 定义并从公共 barrel 导出：

```ts
interface AlarmEvent {
  id: string;
  message: string;
  area: string;
  occurredAt: string;
  acknowledgedAt: string | null;
}
```

- PostgreSQL `bigint` ID 在 API 中使用十进制字符串，禁止转为 JavaScript `number`。
- 时间字段使用 ISO-8601 字符串；数据库字段名不直接暴露给前端。

### HTTP API

```text
GET   /api/alarms/latest
GET   /api/alarms?days=1&page=1
PATCH /api/alarms/:id/acknowledgement
POST  /api/alarms/acknowledgements
```

- `GET /api/alarms/latest` 返回 `AlarmEvent[]`，按 `occurred_at DESC, id DESC` 查询全部历史中的最新两条。
- 历史查询的 `days` 只允许 `1 | 3 | 10 | 30`，默认 `1`；时间范围均为从请求时刻向前滚动，1 个月按 30 天计算。
- 历史查询每页固定 20 条，不接受自定义 `pageSize`，返回 `{ items, page, pageSize, total }`。
- 翻页和刷新时重新计算时间窗口，接受新事件导致当前页内容移动。
- 单条确认仅在 `acknowledged_at IS NULL` 时写入数据库；重复确认保持首次确认时间并幂等成功。
- 批量请求体为 `{ ids: string[] }`，仅提交当前页面可见的未确认 ID，单次最多 20 个；使用一个数据库语句完成确认。
- 批量确认忽略不存在或已确认的 ID，返回 `{ acknowledgedCount: number }`，只统计本次首次确认数量。
- 单条目标不存在返回 404；非法 ID、查询参数或请求体返回 400；数据库错误返回 500。
- 确认写入成功但 Redis 通知失败时，HTTP 仍返回成功并记录错误。
- 所有能访问系统的用户均可确认报警。本期后端没有可信身份校验，因此不记录确认人、不实现角色权限。

### 实时通知

- Web 后端复用现有 Redis Pub/Sub 客户端，同时订阅 `RealDataChanged` 和 `AlarmChanged`，不得创建第三条 Redis 连接。
- 新增独立 Socket.IO 事件 `alarm:changed`，不得借用 `data:push` 或实时 tag 订阅。
- C++ 新增报警后向 `AlarmChanged` 发布事件 ID。
- Web 确认单条报警后发布该事件 ID；批量确认后发布固定值 `0`，表示多条记录已变化。
- Redis 消息只允许十进制正整数事件 ID 或固定值 `0`；非法消息只记录日志且不广播。
- Web 后端收到有效通知后向所有 Socket.IO 客户端广播 `alarm:changed`；消息仅作为重新查询信号，不作为报警数据。
- Redis 不可用时 HTTP 查询和确认继续工作；订阅恢复后自动重新订阅。

## Web 前端

### 数据刷新

- 页头组件和报警页面在首次加载、Socket.IO 重连、收到 `alarm:changed`、页面重新可见时查询数据。
- 可见页面每 30 秒轮询一次；浏览器页面不可见时暂停轮询。
- 连续刷新请求需要合并：同一时刻只允许一个请求在途，结束后最多补一次刷新，保证最终读取最新数据。
- 查询失败时保留上次成功数据并显示“报警数据更新失败”，不得清空为无报警状态。
- 确认成功后立即在本地标记，再后台重新查询校正；失败时恢复未确认样式并显示错误提示。

### 页头报警组件

- 在 `HomePage.vue` 使用的 `AppHeader` 中加入紧凑报警组件，同时保留系统标题并缩小其占位。
- 固定显示全部历史中最新两条报警的发生时间和消息；已确认和未确认记录均显示。
- 未确认行显示红色，已确认行使用普通样式。
- 消息单行截断，悬停显示全文。
- 点击未确认行立即确认，不弹二次确认框；点击已确认行不执行任何操作。
- 没有任何记录时显示“暂无报警记录”，避免表达成当前设备无故障。

### 报警查询页面

- 新增 `/alarms` 子路由，所有用户可访问，使用 `1920 x 1080` HMI 缩放。
- 在侧栏和页脚第 6 个槽位增加“报警查询”入口。
- 页面风格与 `frontend/src/views/MainMonitorView.vue` 保持一致，固定全屏且无页面滚动。
- 使用 Select 选择最近 1 天、3 天、10 天或 30 天，默认最近 1 天；切换范围后回到第一页。
- 表格按发生时间和 ID 倒序显示时间、区域、报警信息和确认状态，每页固定 20 条。
- 时间固定按 `Asia/Shanghai` 显示为 `YYYY-MM-DD HH:mm:ss`，不依赖操作终端时区。
- 消息最多显示两行，悬停显示全文；未确认行显示红色。
- 点击未确认行立即确认；已确认行不执行操作。
- “确认当前页”只提交点击瞬间当前页可见的未确认 ID，不确认请求期间新到达的报警。
- 所选时间范围无记录时显示“所选时间范围内无报警”。

## 故障与一致性原则

- 数据库提交是发布或确认成功的判定点，Redis 和 Socket.IO 只负责降低刷新延迟。
- Redis 通知可能丢失，首次查询、重连刷新、可见性刷新和 30 秒轮询保证最终一致。
- 报警风暴期间通过请求合并控制查询并发，不丢弃最终刷新。
- PostgreSQL 运行中断时发布失败不阻断 TubeTrack 生产流程；连接重建属于整个 TubeTrack 的独立改造范围。

## 部署顺序

三个步骤必须按顺序执行：

1. 执行 `gt4_web/doc/database/alarm_event.sql`。
2. 部署 `gt4_web` 后端与前端。
3. 部署 `gt4_app`。

## 验收标准

1. 每次有效 `publish()` 在数据库新增独立记录，时间由数据库生成，随后触发 Web 实时刷新。
2. 空消息和超长区域被拒绝；数据库失败返回失败，通知失败不制造重复报警。
3. 页头始终展示最新两条历史记录，并能幂等确认未确认报警。
4. 报警页面按四种滚动时间范围查询、固定分页，并能确认单条或当前页报警。
5. 多客户端在新增或确认后均刷新；Redis 中断期间仍可查询和确认，轮询能恢复显示一致性。
6. 未确认、已确认、空数据、加载失败和确认失败均有明确且不误导的界面状态。
7. `gt4_app` 完成 AlarmPublisher 与 TubeTrack 目标构建；`gt4_web` 的 shared、backend、frontend 均通过类型检查、lint 和构建。
