# bundle-transactional-save Specification

## Purpose

定义管捆和管子数据的保存、校验和事务替换行为，确保保存结果一致、可回滚，并向前端返回明确的成功或失败状态。

## ADDED Requirements

### Requirement: 系统必须在保存前执行前端完整性校验

系统 SHALL 在用户点击“保存”时先校验当前管捆草稿和管子列表；若任一必填条件不满足，系统 MUST 阻止提交并提示用户修正数据。

#### Scenario: 管捆信息存在空值时阻止保存

- **GIVEN** 当前管捆草稿仍有任一必填字段为空
- **WHEN** 用户点击“保存”
- **THEN** 系统必须阻止向后端提交保存请求
- **AND** 系统必须提示用户管捆信息不能为空

#### Scenario: 管子记录为空时阻止保存

- **GIVEN** 当前管捆草稿的管子列表为空
- **WHEN** 用户点击“保存”
- **THEN** 系统必须阻止向后端提交保存请求
- **AND** 系统必须提示用户至少需要一条管子记录

#### Scenario: 管子关键字段小于等于零时阻止保存

- **GIVEN** 当前管子列表中存在流水号、管号、重量或长度小于等于 `0` 的记录
- **WHEN** 用户点击“保存”
- **THEN** 系统必须阻止向后端提交保存请求
- **AND** 系统必须提示用户这些字段必须大于 `0`

### Requirement: 系统必须以完整载荷提交管捆和管子数据

系统 SHALL 在前端校验通过后，将当前完整的管捆草稿和全部管子记录一起提交到后端，包括页面未显示但保存所需的字段。

#### Scenario: 保存请求包含完整管捆字段

- **GIVEN** 当前草稿包含页面显示字段和隐藏字段
- **WHEN** 前端发起保存请求
- **THEN** 请求体必须包含完整的管捆数据对象
- **AND** 不得因页面未显示而省略已有字段

#### Scenario: 保存请求包含全部管子记录

- **GIVEN** 当前草稿包含 5 条管子记录
- **WHEN** 前端发起保存请求
- **THEN** 请求体必须包含这 5 条管子记录的完整集合
- **AND** 后端必须按该集合作为本次保存的最终内容处理

### Requirement: 后端必须以事务方式替换目标管捆及其管子数据

系统 SHALL 在接收到有效保存请求后，对同一合同号、项目号、管捆号对应的管捆和管子数据执行事务型替换；任一步失败时，系统 MUST 回滚全部数据库操作。

#### Scenario: 保存时先删除旧数据再写入新数据

- **GIVEN** 数据库中已存在相同合同号、项目号、管捆号的旧管捆和旧管子数据
- **WHEN** 后端执行保存事务
- **THEN** 系统必须先删除该键值下的全部旧管子数据
- **AND** 再删除该键值下的旧管捆数据
- **AND** 再插入新的管捆数据和新的全部管子数据

#### Scenario: 任一步失败时整体回滚

- **GIVEN** 后端已开始执行保存事务
- **WHEN** 删除或插入任一步骤发生错误
- **THEN** 系统必须回滚本次事务中的全部数据库修改
- **AND** 数据库中不得留下部分删除或部分新增的数据

### Requirement: 系统必须在保存时再次保障业务唯一性和结果反馈

系统 SHALL 在后端保存流程中再次校验同合同号、项目号下的管捆号唯一性，并将保存成功或失败的结果明确返回给前端。

#### Scenario: 保存时发现管捆号冲突则返回失败

- **GIVEN** 前端提交的管捆号在相同合同号和项目号下已被其他记录占用
- **WHEN** 后端执行保存校验
- **THEN** 系统必须拒绝本次保存
- **AND** 系统必须向前端返回明确的冲突失败结果

#### Scenario: 保存成功后返回成功结果

- **GIVEN** 前端提交的管捆和管子数据全部合法且事务执行成功
- **WHEN** 后端完成保存
- **THEN** 系统必须向前端返回保存成功的结果
- **AND** 前端必须能够据此提示用户保存成功
